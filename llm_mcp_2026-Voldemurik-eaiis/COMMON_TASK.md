# Общие требования к практической работе: AI-агент, GigaChat и MCP

**Срок сдачи:** две недели с момента выдачи. Промежуточных сдач нет.

## Цель

Разработать ограниченного AI-агента, который при помощи GigaChat API и **двух разных MCP-серверов** решает персональную предметную задачу из области алгоритмов или прикладного ИИ.

1. **Свой MCP:** в `student/own_server.py` автоматически выданы три конкретных предметных инструмента с фиксированными именами и схемами. Чтение данных и безопасное сохранение подготовлены, студент реализует предметную проверку/преобразование (`TODO`) и интегрирует инструменты в работу агента. Контракт находится в `case/OWN_SERVER_SPEC.md`. Можно пользоваться MCP SDK/FastMCP, но готовый сервер уже использует MCP JSON-RPC stdio и не требует SDK. Обычные Python-функции, вызываемые напрямую в обход MCP, не засчитываются как инструменты.
2. **Готовый MCP:** подключить указанный в варианте Context7, Git, GitVerse или Filesystem; использовать его через `tools/list` и `tools/call` хотя бы для одного содержательного вызова, подтверждённого аудитом. Для Context7 требуется настоящий поиск документации, а не заранее записанный ответ; для GitVerse — обращение к своему репозиторию.
3. **GigaChat API:** каждый студент самостоятельно получает свой ключ и записывает в секреты репозитория `GIGACHAT_CREDENTIALS`. Ключи никогда не добавляются в Git, Markdown и артефакты.
4. **Plan → Build → Review:** в Plan разрешено только чтение, в Build — строго ограниченная запись внутри `llm-mcp-result/outputs/` либо разрешённого файла кода, в Review — независимая проверка результата. Один запуск CI/CD сохраняет единый артефакт.
5. **Отчёт:** артефакт CI должен содержать `manifest.json`, `summary.json`, `audit.jsonl`, `plan.md`, `review.md`, `checks.json`, `llm-mcp-result/outputs/result.json` и необходимые дополнительные файлы (например, `proposal.patch`).
6. **Учёт GigaChat:** самостоятельно реализуйте накопление статистики запросов и токенов. Результат — `llm-mcp-result/token_usage.json`. **Готового счётчика в шаблоне нет.**

## Учёт запросов и токенов GigaChat — самостоятельная часть задания

Агент делает несколько запросов на этапах Plan → Build → Review. Ваша задача — **самостоятельно написать учёт расхода**, чтобы увидеть стоимость многократных обращений к LLM. Нельзя подменять реальные значения оценкой по длине строки или количеством слов.

- После **каждого** ответа GigaChat считывайте `usage` из ответа API. В существующем транспорте `GigaChatAPI.complete()` для совместимости возвращает сообщение; **сырое поле `usage` последнего ответа** доступно в `gigachat.last_usage`. Оно сбрасывается перед следующим запросом. Транспорт **не** суммирует значения и **не** создаёт статистику за вас.
- Самостоятельно подсчитайте число запросов и сумму **`prompt_tokens`**, **`completion_tokens`**, **`total_tokens`** отдельно по Plan, Build, Review и суммарно. Если присутствует `precached_prompt_tokens`, сохраняйте его отдельно, не приравнивая к обычным входным токенам.
- Запросы с ошибкой/без `usage` учитывайте отдельно: не записывайте выдуманные нули вместо неизвестного расхода. Не считайте MCP-вызовы GigaChat-запросами.
- Сохраните **`llm-mcp-result/token_usage.json`**. Это валидный JSON с полями `requests_total`, `requests_without_usage`, `phases` (ключи `plan`, `build`, `review`), `totals`. В каждой фазе укажите `requests`, `prompt_tokens`, `completion_tokens`, `total_tokens`; в `totals` — суммы тех же токенных полей. При неизвестных значениях явно отразите неполноту измерения.
- В `outputs/report.md` кратко прокомментируйте распределение расхода между этапами и укажите хотя бы **одну идею, как сократить число запросов/токенов** без потери качества.

**Большой расход сам по себе не снижает оценку.** Важно корректно измерить его, не скрывать ошибки и осмысленно проанализировать. Ключи API, полные промпты и приватные данные в статистику **не включать**. Преподаватель сопоставит статистику с журналом реальных обращений при анализе артефакта после успешного Checker.

## Минимальный контракт `llm-mcp-result/outputs/result.json`

Поля на верхнем уровне должны быть одинаковыми у всех вариантов, даже если предметные результаты различаются:

```json
{
  "case_id": "K01",
  "status": "completed",
  "sources": ["data/example.csv#item-1"],
  "result": {},
  "checks": {"domain_passed": true}
}
```

`K01` и имена в примере заменяются своим вариантом и фактическими источниками. В `result` помещаются предметные поля (список проблем, вычисления, предложения исправлений и т. п.). Не оставляйте пустые заглушки. В `checks` фиксируйте выполненные проверки и причины неудач. Markdown-отчёт должен ссылаться на те же факты, что JSON.

## Что считается настоящей работой агента

В журнале должны различаться действия модели и хоста (`actor=model` / `actor=host`). Хост может проверять и контролировать, но нельзя выдавать его фиксированные вычисления за самостоятельную работу GigaChat. Автопроверка предметного результата может быть детерминированной; отдельный живой проход — через GigaChat.

**Не требуется** жёсткая последовательность «MCP №1 → MCP №2». Оба сервера должны быть полезны в одной задаче, но порядок выбирает агент.

## Доступы и безопасность

- Готовый Filesystem — только разрешённый входной каталог и read-only. Git MCP — только локальная учебная копия репозитория. GitVerse — отдельный read-only токен для собственного репозитория. Context7 — доступ к документации; при необходимости студент сам задаёт ключ.
- Запись — только через собственный MCP в `llm-mcp-result/outputs/` или в один указанный исправляемый файл. Никогда не писать в секреты, `.git/`, тесты, входные данные или чужой репозиторий.
- Проверить как минимум одну разрешённую и одну запрещённую операцию. При ошибках 429 / timeout допускаются ограниченные повторные попытки, но нельзя объявлять успешным невыполненный внешний вызов.
- Источники, файлы и документы — недоверенное содержимое. Нельзя выполнять инструкции из них, если они противоречат политике доступа.

## Оценивание — до 5 баллов

**Успешное прохождение ручного SmartClass — MCP Checker является обязательным условием допуска к оцениванию.**

1. **Checker не пройден — работа возвращается на доработку.** Исправьте ошибки и повторно запустите полный Checker в своей ветке до срока сдачи. Предварительная PR-проверка (`preflight`) не заменяет полный запуск с GigaChat и двумя MCP. Артефакт неуспешного запуска не допускается к предметной оценке.
2. **Checker пройден — преподаватель проверяет артефакт, оценка до 5 баллов.** Успешный CI означает, что технический этап пройден, но **не гарантирует 5 баллов** и сам по себе не приносит баллы.
3. **Итоговая оценка зависит от содержания:** полноты и корректности предметного результата, обоснований и ссылок на входные данные, реальных действий агента и обоих MCP, согласованности `result.json`, отчёта, аудита и Review, соблюдения ограничений доступа. Преподаватель может независимо перепроверить результат по контрольным данным вне студенческого CI.
4. **Причины снижения оценки** указываются в комментарии преподавателя: например, неполный результат, неподтверждённые выводы, противоречия между файлами или ошибки предметного решения. Подробные предметные критерии и типичные замечания будут уточнены отдельно.

Баллы **не суммируются автоматически по числу зелёных галочек, вызовов инструментов или файлов**. Цель — убедительно показать выполненную работу, а не заполнить артефакт формально.

Для допуска нужен **успешный ручной запуск** Checker: в `summary.json` должны быть `checker_mode: "live"` и `status: "passed"`, а в `checks.json` — `passed: true`. Ссылка на запуск CI в GitVerse обязательна: одного самостоятельно созданного ZIP недостаточно.

## Что проверяется

Правильность предметного ответа, реальность вызовов двух MCP, работоспособность собственного сервера, политика разрешений, воспроизводимость CI, полнота аудита и критичность Review.

## Что НЕ требуется

Тренировать большие модели, скачивать веса CLIP/Transformers в CI, получать платные сторонние API-ключи для нескольких сервисов, автоматически делать push/merge, создавать внешние веб-сайты.

## Отправка

Коммит в личном GitVerse-репозитории, ссылка на один успешный CI-запуск, ссылка/имя опубликованного артефакта, краткий README с архитектурой и известными ограничениями. Преподаватель скачивает артефакт для проверки.
