# Программные заготовки студента

В персональной ветке `student/own_server.py` **уже содержит три конкретных MCP-инструмента** вашего варианта. Их названия и контракты перечислены в `case/OWN_SERVER_SPEC.md` и `TASK.md`.

Вам **не нужно** придумывать имена инструментов и разрабатывать MCP-транспорт. Также не требуется устанавливать тяжёлые ML-библиотеки или скачивать веса моделей.

## Порядок работы

1. Откройте `case/OWN_SERVER_SPEC.md` и прочитайте, что делает каждый инструмент.
2. В `student/own_server.py` найдите `TODO` в **предметной функции** (например, `check_tokenizer_config`). Реализуйте её на основе файлов `case/` стандартными средствами Python. Две другие функции — чтение и безопасная запись — уже готовы.
3. Не переименовывайте инструменты без необходимости. Используйте **настоящие** вызовы MCP через `tools/list`/`tools/call`, а не прямой вызов функций из `student.agent`.
4. В `student/agent.py` **подключение уже подготовлено**: `main()` читает `variant.json`, запускает оба MCP и создаёт `GigaChatAPI`. Заполните три функции: `plan_phase()`, `build_phase()`, `review_phase()`.
   - **Plan:** модель читает реальные сведения через оба MCP и составляет план; запись запрещена программно.
   - **Build:** модель вызывает предметную функцию своего MCP и сохраняет результат инструментом записи в `outputs/`.
   - **Review:** проверьте созданные файлы, затем передайте результаты проверки модели для критического заключения.
   При каждом вызове через MCP пишите `audit.jsonl`: фаза, сервер, инструмент, успех/ошибка, `actor=model` либо `actor=host`.
5. **Самостоятельно реализуйте учёт токенов**: считывайте `gigachat.last_usage` сразу после каждого успешного ответа, накапливайте значения по этапам и сохраняйте `llm-mcp-result/token_usage.json`. Готовой функции подсчёта нет.
6. Запустите ручной SmartClass Checker в своей ветке, исправьте замечания и скачайте артефакт.

`health_check()` — отдельная проверка подключения, **не считается** предметным инструментом.

## Что значит «готовый сервер»

Команда `python -m student.own_server` запускает процесс в **stdio** и ожидает MCP JSON-RPC сообщения. Отсутствие обычного текста в терминале нормально. Не печатайте отладочные сообщения в stdout — он зарезервирован для протокола.

Пока предметная функция не реализована, она возвращает `NotImplementedError` через MCP. Это ожидаемая незавершённость заготовки, а не ошибка GitVerse. Изначально Checker не должен быть зелёным.

Можно расширять структуру `student/`, добавлять тесты и зависимости, но не менять `course/`, `case/`, `variant.json` и workflow.

## Как читать `student/agent.py`

В начале файла есть **шпаргалка по интерфейсам**, а у каждой незаполненной функции — русская инструкция с ожидаемым результатом. Вызов `GigaChatAPI.complete()` сам по себе **не исполняет** MCP-инструмент: `function_call` из ответа надо разобрать, проверить разрешения, вызвать `.call(...)` и передать результат обратно модели.

Служебные файлы `manifest.json`, `plan.md`, `review.md`, `summary.json` создаёт инфраструктурная часть `main()` после успешной работы фаз. Но `outputs/result.json`, `outputs/report.md`, содержательное использование инструментов, `audit.jsonl` и `token_usage.json` — ваша работа.

Не меняйте сигнатуры `plan_phase`, `build_phase`, `review_phase`, пока не разобрались с маршрутизацией данных: `main()` ожидает от них соответственно **текст плана**, **словарь результатов** и **текст проверки**. `NotImplementedError` означает, что функцию ещё надо реализовать. При неизменённых заглушках полноценный Checker закономерно не проходит.

Локальная команда `python -m student.agent --help` показывает параметры, но **не выполняет** вызов GigaChat. Для интеграционного прогона используется ручной Checker в GitVerse; не записывайте секреты в исходники ради локального запуска.
